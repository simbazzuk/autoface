# AutoFace v0.3 — Identity Verification Boundary

## Objective

Add strong identity and liveness evidence without creating passport, driving-licence or biometric upload capabilities inside AutoFace.

## Security boundary

The browser requests a verification session from `/api/verification/start` using the signed-in Firebase user's ID token. The API verifies that token with Firebase Admin, creates a server-controlled `verificationSessions` record, and redirects to the configured provider journey.

In v0.3 development mode the provider journey is deliberately simulated. It collects no identity data. Successful simulation posts back to a server-side completion endpoint. Only trusted server code writes `identityVerified` and `livenessVerified` into Firestore. Firestore rules prevent the browser from self-awarding verification evidence.

## Data AutoFace stores

- verification status
- completed verification checks
- provider name
- opaque provider reference
- verification timestamp
- security-event audit records

## Data AutoFace v0.3 does not provide fields for

- passport images
- driving-licence images
- identity-document numbers
- raw selfies
- raw liveness video
- biometric templates

## Development simulator

Set `AUTOFACE_VERIFICATION_MODE=demo`. The simulator exists only to validate the security boundary and user journey before a production identity provider is selected. A simulated verification must never be presented as a real identity check outside development/test environments.

## Production provider adapter

`lib/server/verification-provider.ts` is the integration seam. When a provider is selected, replace the `provider` branch with that provider's hosted-session creation API and add a provider-signed webhook endpoint. The webhook must validate the provider signature before writing verification evidence.
